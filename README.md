# orbit-local

[Orbit](https://github.com/deltaomega02/orbit)(졸업작품)의 코디 도메인을 **Kotlin + Spring Boot로 이식한 것**입니다.

원본은 Django REST로 만들었고 잘 돌아갔지만, 나중에 코드를 다시 읽으면서 **네 가지가 빠져 있다는 걸 알았습니다** — 인증, 트랜잭션 경계, 테스트, 그리고 목록 조회의 N+1. 이 저장소는 같은 도메인을 다시 만들면서 **그 넷을 기능보다 먼저** 넣은 결과입니다. 문법 연습이 아니라, **제가 놓친 것이 다른 프레임워크에서는 어떻게 다뤄지는지 확인하는 것**이 목적이었습니다.

그 위에 원본의 기능을 다시 올렸습니다. 사진으로 옷 등록, AI 코디 추천, 가상 착용까지 **실제로 쓸 수 있는 앱**입니다. 졸업작품으로 끝내지 않고 더 나은 구조로 다시 세워 보는 것이 이 저장소의 목적입니다.

원본에서 가장 잘한 판단이라고 생각하는 **중복 추천 → HTTP 409 + `retry: true`** 계약은 그대로 가져왔습니다.

```
Kotlin 2.2 · Spring Boot 3.5 · Spring Security · JWT(jjwt) · Spring Data JPA
H2(기본) / MySQL(프로파일) · Gemini API · 바닐라 JS 프론트 · JUnit 5
```

## 실행

```bash
./gradlew test          # 테스트 223개
./gradlew bootRun       # http://127.0.0.1:8080 (H2 파일 DB — 아래 "데이터가 어디에 있나")
```

브라우저로 `http://127.0.0.1:8080` 을 열면 바로 화면이 뜹니다. **로그인 화면은 없습니다** — 한 사람이 자기 노트북에서만 쓰는 앱이라 켜면 곧바로 자기 옷장이 나옵니다(아래 "[1인 전용](#1인-전용--로그인을-없앤-대신-무엇을-내줬나)"). 빌드 도구나 별도 프론트 서버가 필요 없습니다 — 받는 사람이 개발자가 아니어도 실행할 수 있어야 했기 때문입니다.

서버는 **루프백(127.0.0.1)에만 바인딩**합니다(`server.address`). 로그인이 없어진 지금 그 한 줄이 이 앱의 경계입니다. 주소를 `localhost` 가 아니라 `127.0.0.1` 로 적는 이유는 `localhost` 가 기기에 따라 IPv6(`::1`)로 먼저 풀리기 때문입니다.

AI 기능(사진 분석 · 코디 추천 · 가상 착용)을 쓰려면 키가 필요합니다.

```bash
GEMINI_API_KEY='...' ORBIT_JWT_SECRET='...32바이트 이상...' ./gradlew bootRun
```

**키가 없어도 앱은 정상 동작합니다.** AI 엔드포인트만 503을 반환하고 옷장·코디 관리는 그대로 됩니다. 외부 의존이 죽었을 때 서비스 전체가 같이 죽지 않게 하는 것은 원본에서 잘했다고 생각한 판단이라 그대로 가져왔습니다.

MySQL로 붙이려면 `--args='--spring.profiles.active=mysql'`.

JWT 시크릿은 `ORBIT_JWT_SECRET` 환경변수로 주입합니다. 설정하지 않으면 `dev-only-insecure-...`라는 개발용 기본값이 쓰이는데, **이름 그대로 개발용**이고 운영에 올라가면 값만 봐도 사고인 걸 알 수 있게 해 뒀습니다. 실제 시크릿은 저장소에 넣지 않습니다.

```bash
ORBIT_JWT_SECRET='...32바이트 이상...' ./gradlew bootRun
```

**설치본(Windows exe)에서는 다릅니다.** 위 개발용 기본값을 쓰지 않고, 첫 실행에 기기마다 다른 시크릿을 만들어 `%LOCALAPPDATA%\Orbit\jwt.key` 에 두고 그 뒤로 재사용합니다(`OrbitEnvironmentPostProcessor.installDesktopJwtSecret`). 받는 사람에게 "환경변수를 설정하세요"라고 할 수는 없고, 그렇다고 모든 설치본이 저장소에 적힌 같은 값을 쓰는 것은 시크릿이 없는 것과 크게 다르지 않기 때문입니다. `ORBIT_JWT_SECRET` 을 직접 준 경우에는 그 값을 존중합니다.

## Windows 배포본 만들기

받는 사람은 개발자가 아니고 JDK도 없습니다. 그래서 **자바 런타임을 통째로 안고 나가는 실행 파일**로 포장합니다. `jpackage` 는 **크로스 빌드를 하지 못하므로**(macOS에서 Windows exe를 만들 수 없습니다) GitHub Actions의 `windows-latest` 러너에서 만듭니다.

```bash
gh workflow run "Windows パッケージ (jpackage)" --ref main -f version=1.0.0
gh run watch
```

워크플로 파일은 `.github/workflows/windows-package.yml` 입니다. `workflow_dispatch` 로 손으로 돌리거나 `v*` 태그를 밀면 돕니다. **`workflow_dispatch` 는 워크플로 파일이 기본 브랜치에 올라가 있어야 동작합니다** — 브랜치에만 있으면 목록에 뜨지 않습니다.

버전은 **첫 자리를 0으로 두지 않습니다**. jpackage가 이 값을 OS의 버전 규격으로 그대로 옮기는데 거기서 선행 0은 유효하지 않습니다(macOS는 즉시 거부하고, Windows MSI도 ProductVersion 규칙이 따로 있습니다). 코드의 `version = 0.1.0` 과 다른 것은 그래서이고, 이쪽은 **받는 사람에게 건네는 물건의 번호**입니다.

나오는 것은 아티팩트 `orbit-windows-<버전>` 안에 세 가지입니다.

| 파일 | 무엇 |
|---|---|
| `Orbit-<버전>-windows-portable.zip` | **주 배포 형태.** 압축을 풀고 `Orbit.exe` 를 더블클릭하면 끝. 관리자 권한 불필요 |
| `Orbit-<버전>.msi` | 설치형. 러너에 WiX 3이 있을 때만 만들어집니다. 없으면 이것만 빠지고 zip은 그대로 나옵니다 |
| `TESTING-ko.md` | 넘기기 전에 Windows에서 확인할 항목. 배포자용 |

zip 안에는 일본어 안내문 `はじめにお読みください.txt` 가 함께 들어갑니다(원본은 `packaging/windows/`, CI에서 UTF-8 BOM + CRLF로 변환합니다 — 메모장이 인코딩을 잘못 짚으면 안내문 전체가 깨진 글자가 되고, LF만 있으면 옛 메모장에서 한 줄로 뭉칩니다). **SmartScreen 경고를 통과하는 법**이 그 안내문의 핵심입니다 — 서명되지 않은 exe라 첫 실행에 "Windows によって PC が保護されました"가 뜨고, 「詳細情報」→「実行」을 모르면 대부분 여기서 포기합니다.

**API 키는 굽지 않습니다.** 이 저장소는 public이라 CI 아티팩트도 공개됩니다. Gemini 키는 사용자가 앱 화면(その他 → AI連携)에서 직접 넣습니다.

포장된 앱이 개발 실행과 다르게 하는 일:

- 콘솔 창이 없습니다(`--win-console` 을 주지 않습니다). 대신 로그를 `%LOCALAPPDATA%\Orbit\logs\orbit.log` 로 보냅니다 — 화면에 아무것도 안 나오는 앱에서 그 파일이 유일한 단서입니다
- 8080이 막혀 있으면 **빈 포트를 찾아** 쓰고 브라우저를 그 포트로 엽니다(`FreePort`)
- **알림 영역 아이콘이 종료 수단입니다**(`DesktopIntegration`). 브라우저 탭을 닫아도 서버는 살아 있고, 터미널을 쓰지 않는 사용자에게 작업 관리자를 열라고 하는 것은 답이 아닙니다. 기동 직후 풍선 알림으로 그 자리를 한 번 짚어 줍니다
- 두 번째 실행은 죽지 않고 **이미 떠 있는 쪽 화면을 열어 줍니다**(`SingleInstance`)

이 갈래는 `jpackage.app-path` 시스템 프로퍼티로 판단합니다(`DesktopRuntime.launchedFromPackagedApp`). **`./gradlew bootRun` 은 예전 그대로**라 개발 중에 트레이 아이콘이 생기거나 브라우저가 튀어나오지 않습니다.

확인용 환경변수 — 사용자에게 안내할 내용은 아닙니다.

| 변수 | 무엇 |
|---|---|
| `ORBIT_PORT` | 먼저 시도할 포트 (기본 8080) |
| `ORBIT_OPEN_BROWSER=false` | 브라우저 자동 실행만 끕니다 |
| `ORBIT_HOME` | 데이터 폴더를 옮깁니다. 깨끗한 첫 실행을 재현할 때 |

Windows 실행 파일 아이콘은 `packaging/windows/orbit.ico` 이고 `packaging/icon/OrbitIcon.java` 가 만듭니다(`java packaging/icon/OrbitIcon.java packaging/windows/orbit.ico`). 트레이 아이콘과 같은 도형을 같은 규칙으로 그리므로 작업 표시줄과 알림 영역의 그림이 어긋나지 않습니다.

## 데이터가 어디에 있나

설치형 앱이라 사용자 데이터는 프로젝트 폴더가 아니라 **OS가 정해 둔 사용자 데이터 폴더**에 둡니다(`OrbitPaths`). 앱이 놓인 자리는 사용자가 통째로 지우거나 옮기는 곳이고, 거기에 사진과 DB가 있으면 앱을 지우는 순간 옷장도 같이 사라지기 때문입니다.

| | macOS | Windows |
|---|---|---|
| H2 파일 DB | `~/Library/Application Support/Orbit/db/orbit.mv.db` | `%LOCALAPPDATA%\Orbit\db\orbit.mv.db` |
| Gemini 키 | `~/Library/Application Support/Orbit/gemini.key` (600) | `%LOCALAPPDATA%\Orbit\gemini.key` |
| JWT 시크릿 | `~/Library/Application Support/Orbit/jwt.key` (600) | `%LOCALAPPDATA%\Orbit\jwt.key` |
| 이미지 | 실행 디렉터리의 `data/media/` (`ORBIT_MEDIA_DIR`로 변경) | 〃 |

`ORBIT_HOME`으로 데이터 루트 전체를 옮길 수 있습니다.

**감사용 계정을 지우는 법.** 배포본에 남의 계정이 섞여 있으면 안 되므로, 앱을 **종료한 상태에서**(H2 파일은 실행 중 잠깁니다) 아래 SQL을 H2 Shell로 한 번 돌립니다 — 계정 삭제 API는 만들지 않았습니다. 이 앱의 계정 삭제는 배포 전에 한 번 하는 일이지 사용자가 화면에서 누를 일이 아니고, 그 하나를 위해 "다른 계정의 데이터를 지우는 엔드포인트"를 열어두는 편이 훨씬 위험하기 때문입니다.

```bash
java -cp "$(find ~/.gradle/caches -name 'h2-*.jar' | head -1)" org.h2.tools.Shell \
  -url "jdbc:h2:file:$HOME/Library/Application Support/Orbit/db/orbit;MODE=MySQL" -user sa -password '' -sql "
set @u = (select id from users where email = 'sohee.k99@gmail.com');
delete from coordination_item where coordination_id in (select id from coordination where owner_id = @u);
delete from coordination where owner_id = @u;
delete from look_counter where owner_id = @u;
delete from clothes where owner_id = @u;
delete from users where id = @u;"
```

순서가 곧 삭제 순서입니다 — `coordination_item`이 `coordination`·`clothes`를 참조하므로 자식부터 지웁니다. 의류·코디에서 `users`로는 **FK를 걸지 않았기 때문에**(설계 메모의 "User는 엔티티, 소유권은 id 참조") 계정 행만 지우면 옷과 코디가 고아로 남습니다. 그 계정이 올린 이미지 파일은 `data/media/` 아래에 남는데, 참조하는 행이 사라졌으므로 지워도 됩니다(경로를 알고 싶으면 위 SQL 앞에 `select image_path from clothes where owner_id = @u;`를 넣어 확인).

## API

| Method | Path | 인증 | 설명 |
|---|---|---|---|
| `POST` | `/api/auth/session` | — | **자동 세션.** 본문 없음 → 주인의 액세스(15분) + 리프레시(365일) 토큰. 화면이 켜질 때 부르는 유일한 인증 호출 |
| `POST` | `/api/auth/signup` | — | 가입. 이메일 중복이면 **409** *(현재 화면에서는 쓰지 않음)* |
| `POST` | `/api/auth/login` | — | 액세스(15분) + 리프레시(365일) 토큰 발급 *(현재 화면에서는 쓰지 않음)* |
| `POST` | `/api/auth/refresh` | — | 리프레시 토큰으로 액세스 토큰 재발급 *(현재 화면에서는 쓰지 않음)* |
| `POST` | `/api/clothes` | 필요 | 의류 등록 |
| `GET` | `/api/clothes` | 필요 | 의류 목록 (페이지네이션, 기본 20건) |
| `GET` | `/api/clothes/stats` | 필요 | 옷장 통계 — 총계·카테고리별·많이 입은 옷·안 입은 옷 수 |
| `GET` | `/api/clothes/{id}` | 필요 | 의류 상세 |
| `GET` | `/api/clothes/{id}/coordinations` | 필요 | **이 옷이 쓰인 코디들** (페이지네이션) |
| `PATCH` | `/api/clothes/{id}` | 필요 | 의류 수정(보낸 필드만) |
| `DELETE` | `/api/clothes/{id}` | 필요 | 의류 삭제. 코디에 쓰였으면 소프트 삭제 → **204** |
| `POST` | `/api/clothes/analyze` | 필요 | 사진 한 장으로 등록 값 제안. **저장하지 않음** |
| `POST` | `/api/coordinations` | 필요 | 코디 수동 생성. 중복이면 **409** |
| `POST` | `/api/coordinations/recommend` | 필요 | AI 코디 추천. **오늘의 상황**(선택, 100자) 한 줄을 받음. 중복이면 **409 `duplicate`**, 조합을 다 썼으면 **409 `exhausted`** |
| `POST` | `/api/coordinations/{id}/tryon` | 필요 | 가상 착용 이미지 생성(멱등) |
| `DELETE` | `/api/coordinations/{id}/tryon` | 필요 | **가상 착용 이미지만 삭제**(파일까지). 없어도 204 → **204** |
| `GET` | `/api/coordinations` | 필요 | 전체 기록 (최신순, 페이지네이션) |
| `GET` | `/api/coordinations/today` | 필요 | 오늘 만든 코디 목록 |
| `GET` | `/api/coordinations/{id}` | 필요 | 코디 상세 |
| `DELETE` | `/api/coordinations/{id}` | 필요 | 코디 삭제. 가상 착용 이미지 파일도 함께 정리 → **204** |
| `POST` | `/api/coordinations/{id}/favorite` | 필요 | 즐겨찾기 토글. 두 번 누르면 제자리 |
| `PUT` | `/api/users/me/body-photo` | 필요 | 전신 사진 등록(가상 착용용) |
| `GET` | `/api/users/me/style-preference` | 필요 | 스타일 선호도 조회 |
| `PUT` | `/api/users/me/style-preference` | 필요 | 스타일 선호도 저장. **추천 프롬프트에 실제로 들어감** |
| `GET` | `/media/**` | 필요 | 이미지. **소유자만 접근 가능** |

인증이 필요한 경로는 `Authorization: Bearer <액세스 토큰>` 헤더를 받습니다. **소유자는 요청이 지정하는 것이 아니라 서버가 토큰에서 읽습니다** — 요청 본문 어디에도 `ownerId`를 적을 자리가 없습니다.

```bash
TOKEN=$(curl -s -X POST 127.0.0.1:8080/api/auth/session | jq -r .accessToken)

curl -X POST 127.0.0.1:8080/api/coordinations \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"title":"출근룩","clothesIds":[1,2]}'
```

중복이면:

```json
{ "error": "duplicate", "retry": true, "clothesIds": [1, 2] }
```

추천(`/recommend`)에는 409가 하나 더 있습니다. 상태 코드는 같지만 **사용자가 할 일이 다른 사건**이라 `error`로 갈립니다.

```json
{ "error": "exhausted", "retry": false, "detail": "今日つくれる組み合わせ1通りをすべて見ました。服を追加すると新しい組み合わせが出てきます。" }
```

`duplicate`는 "이번 추천이 하필 겹쳤다"라 다시 누르면 다른 조합이 나올 수 있고, `exhausted`는 "더 눌러도 소용없다"입니다. 자세한 판단은 설계 메모의 "다 본 조합을 AI에게 다시 묻지 않는다"에 있습니다.

코디 응답에는 화면이 `LOOK 014`로 보여주는 **`lookNo`(사용자별 순번, `Int`)** 가 함께 내려갑니다. `id`와는 다른 값입니다 — 아래 설계 메모의 "LOOK 번호"를 보세요.

### 옷이 가진 정보

의류는 이름·카테고리 외에 **속성축 다섯**을 갖습니다. 전부 선택이고, 사진 분석이 채워 주며, 사용자가 언제든 고치거나 지울 수 있습니다.

| 필드 | 상한 | 예 |
|---|---|---|
| `color` | 30 | 화이트 · 네이비 · 연청 |
| `subCategory` | 30 | 셔츠 · 니트 · 청바지 · 코트 |
| `material` | 30 | 면 · 울 혼방 · 데님 · 리넨 · 기모 |
| `fit` | 20 | 오버핏 · 슬림 · 와이드 · 레귤러 |
| `season` | 20 | 春・秋 / 夏 / 冬 / オールシーズン ([아래](#ai-출력은-일본어다)) |
| `detail` | 200 | 위 축으로 나뉘지 않는 한 줄 요약 |

**왜 한 줄이 아니라 축으로 나눴나.** 예전에는 `detail` 한 줄에 소재·핏·계절이 뭉쳐 있었습니다. 그런데 "얇은 리넨 셔츠"와 "두꺼운 기모 니트"는 둘 다 `TOP / 화이트`라, 추천이 계절감을 맞추려 해도 맞출 근거가 없었습니다. 축을 나누면 프롬프트의 규칙이 가리킬 대상이 생깁니다 — "`계절:여름`과 `계절:겨울`을 한 벌에 섞지 마라"처럼요. 사진 분석 프롬프트도 카테고리별로 볼 곳을 나눠서 봅니다(상의는 목라인·소매·두께, 하의는 밑단·기장, 아우터는 여밈·보온성).

`season`만 네 값으로 좁혀 두는데, 그건 **AI가 답하는 방식**의 제약입니다(`responseSchema`의 enum, 목록 밖의 값이 오면 버립니다). 사용자가 직접 적을 때는 제약이 없습니다 — 소재와 핏은 계속 새 이름이 생기는 영역이라 서버가 목록을 고정하면 자기 옷을 자기 말로 적을 수 없게 됩니다. 다만 **아는 표기는 저장 직전에 표준값으로 눌러 줍니다**(`Seasons.normalize`) — 이유는 아래 "AI 출력은 일본어다"에 있습니다.

**PATCH 규칙은 전부 같습니다.** 필드를 보내지 않으면(`null`) 그대로 두고, 빈 문자열을 보내면 지웁니다. 대부분을 AI가 채우기 때문에 지우는 길이 특히 중요합니다 — 없으면 잘못 들어간 값을 없애는 방법이 "옷을 지우고 다시 등록"뿐입니다.

기존에 등록된 옷은 이 값들이 전부 `null`이고 **그게 정상입니다.** `ddl-auto: update`가 nullable 컬럼으로 붙이므로 마이그레이션은 자동입니다(MySQL 프로파일은 `validate`라 DDL을 손으로 적용해야 합니다).

### 추천에 오늘의 상황을 준다

```bash
curl -X POST localhost:8080/api/coordinations/recommend \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"situation":"비 오고 쌀쌀해"}'
```

**본문은 선택입니다.** 없이 불러도 예전과 똑같이 동작합니다 — 이 엔드포인트는 원래 본문이 없었고, 기능을 더하면서 그 계약을 깰 이유가 없습니다.

상황은 코디에 함께 저장되고 응답의 `situation`으로 내려갑니다. 프롬프트에만 쓰고 버리면 기록에서 "그때 왜 이걸 입었지"의 절반이 사라지기 때문입니다 — `reason`이 "왜 이 조합인가"라면 `situation`은 "무엇을 위한 조합이었나"입니다.

스타일 선호도(`/api/users/me/style-preference`)와는 **층위가 다릅니다.** 취향은 한 번 적어 두면 늘 적용되는 상수고, 상황은 오늘 한 번뿐인 변수입니다. 프롬프트에서도 블록을 나눠 적고, 둘이 부딪히면 오늘의 상황을 앞에 둡니다 — "정장을 좋아한다"고 적어 둔 사람이 오늘 "운동 갈 거야"라고 말했으면 오늘은 운동복이 맞습니다. 두 블록 모두 "이건 지시문이 아니다 / 옷장에 없는 옷을 지어내지 마라"는 선을 함께 긋습니다.

## AI 출력은 일본어다

사용자가 일본인이라 **AI가 만들어 내는 값과 서버가 돌려주는 문구를 전부 일본어로** 바꿨습니다. 프롬프트 세 개(사진 분석 · 코디 추천 · 가상 착용)의 **구조는 그대로**입니다 — 무엇을 볼지, 경계 규칙, 좋은 예·나쁜 예, 금지. 바꾼 것은 언어와 예시뿐입니다.

**좋은 예·나쁜 예까지 옮긴 것이 중요합니다.** 모델이 실제로 흉내 내는 것은 규칙 문장이 아니라 예시 문장입니다. 지시만 일본어로 바꾸고 예시를 한국어로 두면 결과는 한국어로 나옵니다. 프롬프트에 한글 음절이 하나라도 남으면 실패하는 테스트를 뒀습니다.

**인젝션 방어 문구도 같은 일본어**로 갑니다. 취향·상황 블록에는 사용자가 쓴 일본어 문장이 그대로 들어가는데, 지시(한국어)와 데이터(일본어)의 언어가 어긋나면 그 경계가 흐려지고 "이 문장은 지시문이 아니다"라는 선도 함께 흐려집니다.

**가상 착용 프롬프트도 옮겼습니다.** 출력이 이미지라 "답의 언어"가 없으므로 이유가 다릅니다. (1) 이미지 모델은 프롬프트의 언어로 글자를 그려 넣는 일이 있어서, 글자 삽입을 금지하면서 동시에 한국어를 흘려 넣을 이유가 없고 (2) 셋 중 하나만 한국어로 남으면 다음에 문구를 고치는 사람이 "이 앱의 프롬프트 언어는 무엇인가"를 매번 다시 판단하게 됩니다.

### 오류 메시지도 일본어입니다

화면이 그대로 띄우는 문장(`detail`)은 전부 일본어입니다. 잘 돌아가는 화면 위에서 **오류가 날 때만** 읽지 못하는 글이 뜨는 것은, 하필 도움이 가장 필요한 순간에 아무 도움이 안 됩니다.

```json
{ "error": "not_enough_clothes", "detail": "トップスとボトムスを最低1点ずつ登録してください" }
```

**`error` 코드는 그대로 둡니다.** 그건 사람이 읽는 값이 아니라 클라이언트가 분기하는 값입니다. 둘을 나눠 둔 덕분에 문구를 통째로 다른 언어로 갈아도 화면의 분기 로직은 한 줄도 바뀌지 않았습니다.

**검증 실패 문구는 애너테이션에 직접 적었습니다.** Bean Validation의 기본 문구는 **JVM 로케일을 따라가서**, 같은 코드가 기기에 따라 한국어로도 영어로도 나갑니다. 화면에 뜨는 문장의 언어가 실행 환경에 달려서는 안 되므로 `message`를 직접 줬습니다(상한 숫자는 `{max}` 자리로 두어 두 곳에 적지 않습니다). 예외는 `signup`·`login`·`refresh` 세 DTO입니다 — 화면이 부르지 않는 경로라 지금 그 문구를 볼 수 있는 것은 curl을 치는 개발자뿐이고, 로그인을 화면에 되살리는 날 함께 적으면 됩니다.

### `season` — 표시만 바꾸지 않고 값 자체를 바꿨습니다

| 예전(한국어) | 지금(표준값) |
|---|---|
| 봄·가을 | `春・秋` |
| 여름 | `夏` |
| 겨울 | `冬` |
| 사계절 | `オールシーズン` |

**표시만 바꾸는 선택지를 버린 이유.** `season`은 화면 라벨이면서 동시에 **추천 프롬프트에 실려 나가는 데이터**입니다. 옷 목록에 `季節:夏`처럼 저장된 값이 그대로 적히고, 규칙이 그 값을 직접 가리킵니다(“`季節:夏`와 `季節:冬`을 한 벌에 섞지 마라”). 그래서 저장을 한국어로 두면 (1) 모델은 계속 한국어 라벨을 보고 (2) 일본어로 답하게 된 사진 분석 결과를 되돌리려면 양방향 번역표가 필요하며 (3) 결국 DB 안에 두 언어가 섞입니다. 그 실패는 조용합니다 — 추천은 계속 나오고, 다만 계절 규칙이 절반의 옷에만 걸립니다.

**값을 바꾸는 대가는 기존 데이터와 어긋난다는 것**이고, 그 대가는 두 겹으로 치웠습니다.

- **기동 시 한 번 도는 백필**(`SeasonBackfill`) — 이미 저장된 한국어 값을 표준값으로 옮깁니다. Flyway가 없고 `ddl-auto: update`는 컬럼만 추가해 줄 뿐 값을 바꿔 주지 않으므로, `LookNumberBackfill`과 같은 자리에 같은 방식으로 뒀습니다. 멱등이라 여러 번 돌아도 결과가 같습니다.
- **저장 직전 정규화**(`Seasons.normalize`) — 화면이 아직 한국어 계절 칩을 보내더라도 DB에는 한 언어만 남습니다. 목록에 없는 값(사용자가 손으로 적은 표기)은 그대로 통과합니다.

## 1인 전용 — 로그인을 없앤 대신 무엇을 내줬나

이 앱은 **한 사람이 자기 노트북에서만** 씁니다. 그래서 로그인 화면을 없앴습니다. 앱을 켜면 화면이 `POST /api/auth/session` 을 한 번 부르고, 서버가 **자격증명 없이** 주인의 토큰을 내줍니다.

```bash
curl -X POST 127.0.0.1:8080/api/auth/session
# → {"accessToken":"...","refreshToken":"...","tokenType":"Bearer","expiresIn":900}
```

**JWT와 Spring Security 구조는 그대로입니다.** 지운 것은 "누구인지 묻는 절차"뿐이고, 토큰·필터·소유권 격리·`/media` 보호는 하나도 건드리지 않았습니다. 토큰 없이 `/api/**` 를 부르면 여전히 401입니다. `signup`·`login`·`refresh` 도 남아 있습니다 — 여러 사람이 쓰게 되는 날 되살릴 경로이고, 소유권 격리를 검증하는 테스트들이 그 경로로 진짜 토큰을 받아서 씁니다. **다만 현재 화면에서는 쓰지 않습니다.**

### 이건 보안을 연 결정입니다

정직하게 적습니다. `/api/auth/session` 은 **묻지 않고 내줍니다.** 서버에 닿을 수 있는 쪽은 전부 주인의 옷장을 읽고 쓸 수 있다는 뜻입니다.

- **막은 것 — 기기 밖.** `server.address: 127.0.0.1` 로 루프백에만 바인딩합니다. 이 한 줄이 풀리면 같은 와이파이의 아무나 옷 사진과 코디 기록을 읽고 지울 수 있습니다. 로그인을 없앤 대가로 이 설정이 **기능이 아니라 보안 장치**가 되었으므로, 값을 바꾸기 전에 로그인을 먼저 되살려야 합니다.
- **막지 못한 것 — 같은 기기의 다른 프로세스.** 브라우저 확장, 다른 앱, 이 계정으로 도는 스크립트는 여전히 이 엔드포인트를 부를 수 있고, 부르면 주인의 토큰을 받습니다. 비밀번호를 물었을 때와 비교해 실제로 잃는 것이 정확히 이 차이입니다.
- **받아들인 이유.** 담긴 것이 옷 사진과 코디 기록이고, 기기 한 대에서 혼자 쓰며, 그 기기가 이미 털린 상황이라면 로그인 화면이 지키는 것도 거의 없습니다. 하루 한 번 여는 앱에서 매번 지나야 하는 문턱이 주는 마찰이 이 위험보다 크다고 봤습니다.
- **무효가 되는 조건.** 여러 사람이 쓰거나, 기기 밖에서 접근하거나, 공용 기기에 올라가는 순간입니다. (리프레시 토큰 365일 판단과 같은 조건입니다.)

주인의 계정은 **비밀번호로 로그인할 수 없습니다.** 자동으로 만들 때 아무도 모르는 임의 값을 해시해 넣습니다 — 빈 문자열이나 고정 문자열을 넣으면 그 값을 아는 사람에게 `/api/auth/login` 이 열리기 때문입니다.

### 주인은 누구인가 — 설정과 계정 이어받기

```yaml
orbit:
  owner:
    display-name: "エリ"          # 화면에 보이는 이름. 이 한 줄만 고치면 바뀝니다
    email: "eri@orbit.local"      # 내부 식별자(계정 유니크 키). 화면에 노출하지 않습니다
```

화면에 나가는 것은 `display-name` 뿐입니다. 존칭(`さん` 등)은 설정에 넣지 않았습니다 — 붙일지 말지는 화면 문구의 문제라 이름에 박아 두면 화면이 그 판단을 되돌릴 수 없습니다. 정식 이름을 담는 `full-name` 도 두지 않았습니다. 그 값을 읽는 화면이 하나도 없고, **아무도 읽지 않는 설정은 조용히 실제와 어긋나기** 때문입니다.

문제는 **이미 데이터가 들어 있는 DB에서 기동할 때**입니다. 지금 DB에는 `eriko@orbit.test`(옷 7벌·룩 7개)가 있는데 설정 이메일은 `eri@orbit.local` 입니다. "설정 이메일과 일치하는 계정을 쓴다"는 규칙이면 일치하는 것이 없어 **빈 계정을 새로 만들고**, 사용자는 앱을 켜자마자 텅 빈 옷장을 봅니다. 데이터는 DB에 그대로 있지만 사용자에게는 "옷장을 잃었다"와 구별되지 않습니다.

그래서 규칙을 뒤집었습니다 — **옷장이 있는 사람이 주인입니다.**

1. 이미 주인으로 표시된 계정(`users.is_owner`)이 있으면 그 계정.
2. 없으면 **흔적이 가장 많은 계정**(옷 + 코디 수). 동점이면 설정 이메일과 같은 계정, 그래도 동점이면 가장 먼저 만들어진 계정.
3. 계정이 하나도 없으면 설정값으로 새로 만든다.

**설정 이메일은 계정을 새로 만들 때 쓰는 값**이지 기존 계정을 찾는 열쇠가 아닙니다. 사람이 언제든 바꾸는 값(설정)보다 사람이 쌓은 것(옷장)이 신뢰할 만한 신호입니다. "가장 오래된 계정"도 고려했지만 이 DB에는 감사용 계정이 함께 있어서, 그쪽이 먼저 만들어졌다면 빈 계정을 골라 같은 사고가 납니다.

**흔적을 셀 때는 소프트 삭제된 옷도 셉니다.** 묻는 것이 "지금 옷장에 몇 벌 있는가"가 아니라 "이 계정을 실제로 썼는가"이기 때문입니다.

**판단은 한 번만 하고 DB에 적어 둡니다**(`users.is_owner`). 매 기동마다 다시 계산하면 데이터가 움직일 때 답이 바뀔 수 있고, 주인이 바뀌는 것은 사용자에게 곧 "옷장이 통째로 바뀐다"입니다. 컬럼은 `ddl-auto: update` 로 붙고 기존 행은 `NULL`(= 아직 판단하지 않았다)이라 마이그레이션이 따로 없습니다.

이어받은 계정의 **이메일은 건드리지 않습니다**(식별자를 바꾸는 것은 계정을 옮기는 일입니다). 반대로 **화면 이름은 설정이 진실**이라 기동할 때마다 설정값으로 맞춥니다 — 그래야 "설정 한 줄로 이름을 바꾼다"가 성립합니다.

## 인증 — 원본에서 무엇이 잘못됐고 여기서 무엇을 바꿨나

이 저장소를 만든 가장 큰 이유입니다. 원본 Django의 인증은 이랬습니다.

```python
# 11개 뷰에 그대로 복붙돼 있던 4줄
token = request.headers.get("Authorization", "").replace("Token ", "")
user = User.objects.filter(email=token).first()
if not user:
    return Response(status=401)
```

**토큰이 이메일 문자열 그 자체였습니다.** `Authorization: Token someone@gmail.com` 한 줄이면 그 사람이 됐습니다.

| | 원본 Orbit (Django) | orbit-local (Spring) |
|---|---|---|
| 토큰 | 이메일 평문 | HS256 서명 JWT |
| 위조 | 이메일만 알면 누구든 됨 | 서버 키 서명 없으면 401 — 테스트로 고정 |
| 만료 | 없음. 한 번 새면 영구 | 액세스 15분 / 리프레시 365일 ([근거](#리프레시-토큰을-365일로-늘린-이유)) |
| 검증 위치 | 뷰 11곳에 복붙 | `OncePerRequestFilter` 한 곳 |
| 누락 위험 | 한 뷰에서 빠지면 무방비 | 기본값이 `authenticated()`, 열어줄 경로만 나열 |
| 비밀번호 | (소셜 로그인만, 자체 계정 없음) | BCrypt 해시. 평문 저장 없음 — 테스트로 고정 |
| Google ID 토큰 | 서명 검증 없이 payload 신뢰 | (미구현. 붙인다면 서명·aud·iss 검증 필수) |
| 소유권 조건 | `user=request.user`를 쿼리마다 손으로 | 리포지토리 시그니처가 `ownerId`를 요구 |

컨트롤러에는 인증 코드가 **한 줄도 없습니다.** `@AuthenticationPrincipal user: AuthenticatedUser` 하나로 끝납니다. 원본에서 복붙 4줄 × 11곳이 하던 일이 필터 하나로 모인 것이 이 이식의 핵심입니다.

### 판단한 것들

**jjwt를 골랐습니다.** nimbus-jose-jwt는 JWE·JWK 세트·OIDC까지 다루는 범용 구현이라 지금 필요한 것(대칭키 HS256 서명 하나)에 비해 표면이 넓습니다. jjwt 0.12는 `verifyWith(key)`로 파싱 시 알고리즘이 키에 고정되어 `alg=none`·알고리즘 혼동 공격이 API 수준에서 막힙니다.

**토큰 종류를 클레임에 박고 검증합니다.** 액세스와 리프레시는 같은 키로 서명되므로 서명만으로는 구분되지 않습니다. 종류를 확인하지 않으면 (1) 리프레시 토큰이 그대로 장기 API 키가 되고, (2) 액세스 토큰으로 무한히 갱신할 수 있어 "15분"이라는 노출 상한이 사라집니다. 양방향 모두 테스트가 있습니다.

**리프레시 토큰을 회전시키지 않습니다.** 폐기 저장소 없이 새 리프레시를 내주면 만료가 무한히 밀려 상한이 사실상 없어집니다. 회전을 하려면 이전 토큰을 무효화할 저장소(jti 블랙리스트 등)가 먼저 필요하고, 그건 지금 범위 밖입니다. **즉 현재 구조에는 강제 로그아웃이 없습니다.** 알고 남겨둔 빈칸입니다.

### 리프레시 토큰을 365일로 늘린 이유

처음엔 14일이었습니다. 로그아웃 버튼을 없애기로 하면서 365일로 늘렸고, 이건 명백히 보안을 내주고 편의를 산 거래라 근거를 적어 둡니다.

**늘린 이유.** 이 앱은 하루 한 번 열어 "오늘 뭐 입지"를 보는 개인용 로컬 앱입니다. 리프레시가 14일이면 2주에 한 번은 아무 이유 없이 로그인 화면을 만나게 됩니다. 그런데 **강제 로그아웃 수단이 없는 구조에서 짧은 만료는 공격자를 끊지 못합니다** — 회전도 폐기 저장소도 없으니 토큰을 훔친 쪽은 만료일까지 그냥 씁니다. 정작 끊기는 건 사용자뿐이고, 2주마다 비밀번호를 다시 치게 만드는 대신 얻는 것은 "최악의 경우 노출이 14일에서 멈춘다" 하나입니다.

**대가.** 리프레시 토큰이 새면 **노출 기간이 최대 1년**입니다. 특정 토큰만 무효화할 방법은 여전히 없고, 사고가 났을 때 쓸 수 있는 유일한 수단은 `ORBIT_JWT_SECRET`을 바꿔 **모든** 사용자의 토큰을 한꺼번에 죽이는 것뿐입니다. 14일일 때는 "가만히 두면 2주 뒤 알아서 끊긴다"가 최후의 안전망이었는데, 그 안전망을 1년으로 늘린 것이 이 변경의 실체입니다.

**그래도 받아들인 이유.** (1) 담긴 데이터가 옷 사진과 코디 기록이고, (2) 사용자가 자기 기기 한 대에서 쓰는 로컬 앱이며, (3) 토큰이 그 기기의 브라우저 저장소 밖으로 나가지 않습니다. 토큰이 샜다는 건 이미 그 기기가 털렸다는 뜻이고, 그 상황에서 1년이냐 14일이냐는 큰 차이를 만들지 않습니다.

**액세스 토큰 15분은 그대로 둡니다.** 매 요청에 실려 다녀 노출 빈도가 훨씬 높고, 무상태 검증이라 탈퇴·차단 반영 지연의 상한이기도 합니다. 늘려서 얻는 편의(재발급 호출 감소)는 사용자가 체감하지도 못합니다 — 재발급은 화면 뒤에서 자동으로 일어나니까요.

**이 판단이 무효가 되는 조건**은 분명합니다. 여러 사람이 쓰거나, 기기 밖에서 접근하거나, 공용 기기에 올라가는 순간입니다. 그때는 리프레시 회전 + jti 폐기 저장소를 먼저 넣고 이 값을 다시 줄여야 합니다.

**액세스 토큰 검증에 DB를 보지 않습니다.** 요청마다 사용자 조회를 하면 무상태의 이점이 사라집니다. 대신 탈퇴·차단이 즉시 반영되지 않으므로, **반영 지연의 상한이 곧 액세스 토큰 만료(15분)**입니다. 그래서 짧게 잡았습니다. 재발급은 요청량이 적어 거기서만 사용자 존재를 확인합니다.

**남의 리소스에는 403이 아니라 404입니다.** 403은 "그 id는 실재한다"를 알려줍니다. id를 1부터 훑으면 남이 옷을 몇 벌 가졌는지까지 셀 수 있습니다. 권한이 없는 쪽에서는 없는 것과 구별되지 않아야 합니다. 인증 자체가 없을 때만 401로 구분합니다(그건 존재 여부와 무관한 정보입니다).

**로그인 실패 응답을 하나로 통일했습니다.** "이메일이 없습니다"와 "비밀번호가 틀렸습니다"를 구분해 주면 로그인 API가 곧 가입 여부 조회 API가 됩니다. 두 응답이 바이트 단위로 같은지 테스트로 확인합니다.

## 설계 메모

**중복 판정을 서버가 한다.** 추천 엔진은 확률적이라 같은 옷장·같은 조건이면 같은 조합을 반복합니다. 프롬프트에 "같은 걸 내지 마라"를 넣는 건 보장이 아니라 요청이라, 무시될 수 있습니다. 그래서 서버가 당일 코디를 **의류 id 집합으로 비교**해 검증하고, 중복이면 409로 거부합니다. 순서만 다른 조합도 같은 것으로 봅니다.

**추천의 구성도 서버가 다시 본다.** 같은 원칙의 두 번째 적용입니다. 프롬프트에는 "상의 1벌·하의 1벌은 반드시 고른다"가 적혀 있었지만 서버는 그걸 검증하지 않았습니다 — 모델이 상의만 돌려주면 **바지 없는 LOOK이 그대로 저장**됩니다. id 검증만으로는 잡히지 않습니다. 상의만 고른 응답의 id는 전부 진짜니까요. 지금은 소유 검증 다음에 구성을 셉니다. **상의 정확히 1 · 하의 정확히 1 · 아우터 0 또는 1**, 그 밖은 `AiInvalidResponseException` → 502입니다.

규격을 벗어난 응답을 **잘라내지 않고 거절하는** 것이 판단이 갈린 지점입니다. 상의가 둘이면 하나를 버리고 저장할 수도 있지만, 그러면 `reason`이 설명하는 조합과 실제로 저장된 조합이 어긋납니다 — "네이비 셔츠에 카디건을 얹었어요"라고 적힌 코디에 카디건이 없는 상태가 됩니다. **이 앱에서 사용자가 다시 보는 것은 조합보다 이유 쪽**이라, 조합이 하나 모자란 것보다 설명이 거짓말이 되는 쪽이 나쁩니다. 아우터가 **없는 것은 정상**입니다 — 여름에 아우터를 얹는 편이 오히려 틀렸습니다. 이 규격은 아래 "다 본 조합"의 조합 수 식과 같은 모양이어야 하고, 둘 중 하나만 고치면 "다 봤다" 판정이 실제와 어긋납니다.

**N:M을 중간 엔티티로.** 옷은 겹쳐 입기 때문에 코디–의류 관계에 **레이어 순서**라는 속성이 붙습니다. `@ManyToMany`로는 표현이 안 돼서 `CoordinationItem`을 명시적으로 두고, `(coordination_id, clothes_id)`에 유니크 제약을 걸었습니다.

**User는 엔티티, 소유권은 id 참조.** `Clothes.ownerId`에 `@ManyToOne User`를 걸지 않았습니다. 소유권 격리에 필요한 건 id 비교뿐인데 연관을 걸면 조회마다 쓰지도 않을 User를 끌고 오게 되고, 무엇보다 User와 Clothes는 다른 애그리거트라 id로 참조하는 편이 경계를 흐리지 않습니다. 대가로 DB FK가 없어 사용자 삭제 기능을 붙이는 시점에는 정리 로직이 필요합니다.

**트랜잭션 경계.** 코디 1건과 아이템 N건은 하나의 애그리거트로 묶어 `@Transactional` 안에서 저장합니다. Django 버전에서는 이게 없어서 중간에 실패하면 아이템이 비어 있는 코디가 남을 수 있었습니다. → `PersistenceBehaviorTest`

**N+1을 테스트로 고정.** 목록 조회는 fetch join으로 한 번에 읽습니다. 그런데 "지금 안 나는 것"과 "앞으로도 안 나는 것"은 다르므로, Hibernate 통계로 **실행된 쿼리 수를 직접 셉니다**. 오늘의 코디는 코디 3건·아이템 7건을 읽어도 1회입니다. `open-in-view: false`로 둬서 뷰에서 지연 로딩이 몰래 열리지 않게 했습니다.

**컬렉션 fetch join에 페이지네이션을 붙이면 페이지네이션이 조용히 사라진다.** 전체 기록 목록(`GET /api/coordinations`)을 만들면서 부딪힌 지점입니다. 조인 결과의 한 행은 코디가 아니라 "코디 × 아이템"이라, DB에서 20행을 자르면 코디가 20개 나오는 게 아니라 중간에서 잘린 코디가 나옵니다. Hibernate는 이걸 알기 때문에 **전부 읽어 메모리에서 자르고**(`HHH000104`) 경고만 남깁니다 — 즉 원본에서 목록이 항상 전체를 반환하던 것과 사실상 같은 상태가 됩니다. 그래서 ① id만 페이지네이션해서 가져오고 ② 그 id들의 코디를 아이템·의류까지 한 번에 fetch join하는 두 단계로 나눴습니다. 쿼리는 count + id + fetch로 **항상 3회**이고, 코디가 3건이든 10건이든 그대로인지를 테스트가 셉니다. 옷별 코디 역참조(`/api/clothes/{id}/coordinations`)와 옷장 통계도 같은 방식으로 고정했습니다.

**옷 삭제를 409에서 소프트 삭제로 바꿨다.** 원래는 코디에 물린 옷을 지우려 하면 409(`clothes_in_use`)로 거절했습니다. 기록이 깨지는 건 막았지만, **"과거 기록을 보는 앱"에서 한 번 입은 옷을 영영 못 지우게 되는 쪽이 더 이상한 동작**이었습니다. 실제로는 옷을 버리고 나서도 지난 코디는 남아 있어야 하는 게 맞습니다. 두 요구는 사실 충돌하지 않습니다 — **옷장은 "지금 입을 수 있는 옷"을, 기록은 "그때 입은 옷"을 원하기 때문**입니다. 그래서 행을 남긴 채 숨깁니다.

| | 동작 | 이미지 파일 |
|---|---|---|
| 코디에 쓰인 적 **없는** 옷 | 행까지 물리 삭제 | 함께 삭제(참조가 없으니 두면 고아 파일) |
| 코디에 쓰인 적 **있는** 옷 | `deleted_at`만 채움 → 옷장·통계·추천 후보에서 제외 | 남김(과거 코디 화면이 여전히 보여줌) |

어느 쪽이든 응답은 204로 같습니다. 사용자가 "왜 어떤 옷은 지워지고 어떤 옷은 안 지워지는가"를 이해해야 할 이유가 없기 때문입니다. 소프트 삭제된 옷은 상세·수정·재삭제 모두 404이고, 새 코디의 재료로도 쓸 수 없습니다. 대가는 **옷장 조회 쿼리마다 `deleted_at is null` 조건이 붙는다는 것**이고, 하나만 빠져도 지운 옷이 되살아납니다. 그래서 조건을 리포지토리 메서드 이름에 박아 뒀습니다(`findAllByOwnerIdAndDeletedAtIsNull`) — 조건 없는 조회를 부르려 하면 메서드가 없어서 컴파일이 멈춥니다. 일부러 조건을 빼는 곳은 `/media` 소유권 검사 한 곳뿐입니다. "옷장에 있는가"와 "이 파일을 볼 권한이 있는가"는 다른 질문이니까요.

**LOOK 번호는 계산하지 않고 저장한다.** 화면이 `LOOK 014`로 보여주던 번호는 원래 **DB의 `id`를 세 자리로 채워** 만든 값이었습니다. 두 가지가 틀렸습니다. ① `id`는 전역 시퀀스라 사용자가 둘만 돼도 내 첫 코디가 `LOOK 037`로 시작합니다. ② 목록 순서 같은 걸로 다시 계산하면 앞의 코디를 지우는 순간 뒤 번호가 통째로 밀립니다 — 어제 본 `LOOK 005`가 오늘 `LOOK 004`가 되는 기록 앱은 기록 앱이 아닙니다. 그래서 **생성 시점에 사용자별 순번(`look_no`)을 부여해 저장하고**, 응답의 `lookNo`로 그대로 내려줍니다.

**구멍은 그대로 둡니다(004 / 003 / 001).** QA에서 "002 어디 갔지?"가 나왔지만, 그건 사실 정확한 독해입니다 — 002는 있었고 사용자가 지웠습니다. 빈 번호는 삭제의 흔적이지 결함이 아닙니다. 반대로 **지운 번호를 다시 쓰면 "LOOK 002"가 가리키는 대상이 바뀝니다.** 스크린샷을 남기거나 "2번 코디 좋았는데"로 기억하는 곳에서 그건 번호가 하나 비는 것보다 훨씬 나쁩니다. 그래서 발급 이력을 `look_counter` 테이블에 사용자별로 따로 기억합니다. 남아 있는 코디의 `max(look_no) + 1`로 계산하면 **마지막 코디를 지운 직후 그 번호가 재사용되기 때문**입니다(코디는 물리 삭제라 지워진 번호가 코디 테이블에 흔적을 남기지 않습니다).

**겹침은 "아마 안 겹칠 것"으로 두지 않았습니다.** 단일 사용자 로컬 앱이라 확률은 낮지만, 추천이 중복 조합으로 409를 받고 곧바로 재시도하는 **짧은 간격의 연속 생성**이 실제 동작에 있습니다. 세 겹으로 막습니다. ① `(owner_id, look_no)` **유니크 제약** — 겹치면 반드시 실패한다는 DB 차원의 보장 ② 카운터 행을 `select … for update`로 잠그고 번호를 발급 — 두 번째 요청은 실패하는 대신 기다렸다 다음 번호를 받습니다(락 범위가 그 사용자의 카운터 행이라 다른 사용자는 막지 않습니다) ③ 그래도 부딪히면(첫 코디를 만들며 카운터 행 자체를 만드는 순간은 잠글 행이 없습니다) **새 트랜잭션에서 재시도** — 그래서 재시도 루프가 트랜잭션 경계 **밖**에 있고, 그것이 `CoordinationService`(재시도)와 `CoordinationCreator`(시도 1회 = 트랜잭션 1회)가 나뉜 이유입니다. 롤백된 트랜잭션 안에서는 재시도할 수 없습니다. 번호 발급을 별도 트랜잭션으로 먼저 커밋하는 방법도 있지만, 그러면 409로 되돌아간 시도마다 번호가 하나씩 날아가 **삭제한 적도 없는 사용자의 목록이 001 다음 005**가 됩니다.

**기존 데이터는 기동 시 채웁니다.** 이 프로젝트에는 Flyway가 없고 스키마는 `ddl-auto: update`로 따라오는데, 그건 컬럼을 추가해 줄 뿐 값을 채워 주지 않습니다. 이미 앱을 쓰고 있어 데이터가 있으므로 `LookNumberBackfill`이 기동 시(요청을 받기 시작하기 전에) 번호 없는 행을 **생성 시각 순서대로** 채우고 카운터를 맞춥니다. 여러 번 돌아도 결과가 같고, 도중에 죽어도 다음 기동이 이어서 채웁니다. `look_no`가 nullable인 것도 이 때문입니다 — 기존 행이 있는 상태에서 `not null` 컬럼은 애초에 추가되지 않고, 기본값을 주면 모든 기존 행이 같은 값이 되어 위 유니크 제약을 위반합니다.

**다 본 조합을 AI에게 다시 묻지 않는다.** 중복 회피 세 겹(프롬프트 → 서버 판정 → 409 재시도)은 전부 **일단 불러 보고 판정한다**에 서 있었습니다. 그래서 상의 1벌·하의 1벌뿐인 사용자가 두 번째 추천을 누르면, 가능한 조합이 산수로 이미 1개인데도 AI를 부르고 409를 받고 재시도하기를 3번 반복한 뒤에야 "조합을 다 봤어요"가 떴습니다 — **신규 사용자가 가장 먼저 마주치는 상태에서 40초와 세 번의 과금이 확정적으로 낭비**됩니다. 지금은 호출 **전에** 셉니다.

```
가능한 조합 수 = 상의 수 × 하의 수 × (아우터 수 + 1)
```

`+1`은 "아우터를 안 입는 경우"를 세는 항입니다. 이 식은 추천 프롬프트의 규칙 1번("상의 1벌과 하의 1벌은 반드시, 아우터는 어울릴 때만 1벌")과 **같은 것을 말해야 합니다** — 어긋나면 판정이 틀리므로 규칙을 고칠 때 식도 같이 고칩니다(`RecommendableCombinations`).

이미 쓴 조합을 셀 때는 오늘 코디를 그냥 세지 않고 **추천이 만들 수 있는 모양인 것만** 셉니다. 수동 생성은 이 규칙을 따르지 않아서(상의만 있는 코디도 만들 수 있습니다) 조합 공간 안에 있지 않고, 그런 코디를 세면 아직 남은 조합이 있는데도 "다 봤다"고 막게 됩니다. 소프트 삭제된 옷이 낀 조합도 같은 이유로 제외합니다 — 그 옷은 지금 옷장에 없어 다시 추천될 수 없습니다. 덕분에 이 판정은 **한쪽으로만 틀립니다**. 적게 세면 AI를 한 번 더 부를 뿐이고(그 뒤는 기존 duplicate 흐름이 받습니다), 아직 남았는데 막는 일은 일어나지 않습니다. 사용자에게서 가능한 조합을 빼앗는 쪽이 호출 한 번을 낭비하는 쪽보다 나쁘기 때문에 의도적으로 이 방향을 골랐습니다.

`duplicate`와 코드를 나눈 이유도 같습니다. 둘을 뭉뚱그리면 클라이언트가 아는 것은 "재시도"뿐이라, 결과가 정해진 상태에서 계속 누르게 됩니다. `error`로 구분하고 `retry: false`를 함께 실어 **재시도 여부만 보는 클라이언트도 틀리지 않게** 했습니다.

**가상 착용 이미지만 지우는 길을 냈다.** 전에는 결과가 마음에 안 들면 **룩 전체를 지우는 수밖에** 없었습니다. 그런데 합성이 엉뚱한 사람으로 나오는 일은 실제로 있고, 그때 사용자가 버리고 싶은 것은 **이미지 한 장**이지 조합·추천 이유·LOOK 번호가 아닙니다. 게다가 생성이 멱등이라(이미 있으면 다시 만들지 않습니다) 지우는 길이 없으면 한 번 잘못 나온 결과에 영영 묶입니다. `DELETE /api/coordinations/{id}/tryon`은 이미지 행과 파일만 지우고 코디는 남깁니다. **지울 이미지가 없어도 204**입니다 — 결과 상태가 같은데 404를 주면 클라이언트가 지우기 전에 조회를 한 번 더 해야 하고, 두 번 누른 사용자에게 실패처럼 보입니다. 반면 **남의 코디와 없는 코디는 404**입니다. 그건 "이미 그 상태"가 아니라 애초에 다룰 자격이 없는 자원이기 때문입니다.

**Gemini 키는 계정이 아니라 기기에 묶는다.** 새 계정을 만들면 기존 계정이 넣어 둔 키를 그대로 쓰게 됩니다. 감사에서 지적된 그대로이고, **알고 그렇게 둔 동작입니다.** 근거는 셋입니다. ① 키가 실제로 묶이는 대상은 앱 계정이 아니라 **OS 계정**입니다 — 값은 사용자 프로필 안의 파일에 600으로 들어가고, 그 파일에 닿을 수 있는 사람은 앱 계정을 새로 만들어 로그인하는 것도 언제든 할 수 있어서 앱 계정으로 칸을 나눠도 **지켜 주는 것이 아무것도 없습니다**(보안이 아니라 모양이 됩니다). ② 계정별로 두려면 키를 DB나 계정 수만큼의 파일로 옮겨야 하는데, DB 파일은 통째로 백업·복사되는 대상이라 지금의 "파일 하나, 소유자만 읽기"보다 오히려 새는 면이 넓어집니다. 보관 위치를 나쁘게 바꿔서 얻는 것이 "혼자 쓰는 앱에서의 칸막이"뿐입니다. ③ 이 앱의 계정은 보안 경계가 아니라 **옷장의 소유자**입니다. 초대도 공유도 없고 둘째 계정은 사실상 "다시 시작하기"에 가까운데, 그때마다 키를 다시 발급받아 붙여넣게 하는 것은 같은 사람에게 같은 일을 두 번 시키는 것입니다.

대가는 분명합니다. **이 기기를 남과 함께 쓰면 그 사람도 내 키로 AI를 호출할 수 있고 요금은 나에게 청구됩니다.** 그러므로 숨기지 않고 화면 문구로 드러나야 합니다 — "이 기기의 Orbit에만 저장돼요"는 계정별로도 읽히므로 사실과 어긋납니다. **"이 기기의 Orbit 전체에 적용돼요(계정을 새로 만들어도 같은 키를 씁니다)"** 쪽이 맞습니다. 문서만으로는 지켜지지 않으므로 "계정이 달라도 같은 상태가 보인다"를 테스트로 박아 뒀습니다(`GeminiKeyScopeTest`) — 누가 나중에 계정별로 바꾸면 테스트가 깨지고 이 판단을 다시 읽게 됩니다. **뒤집히는 조건**도 적어 둡니다. 한 기기를 여러 사람이 각자의 계정으로 쓰는 것이 실제 사용 방식이 되면 ①과 ③의 전제가 무너지므로 그때는 계정별로 옮겨야 하고, 이미 저장된 키를 첫 사용자에게 귀속시키는 마이그레이션이 필요합니다. 지금은 그 사용 방식이 없습니다.

**코디를 지우면 가상 착용 이미지도 지운다.** 파일 삭제는 **커밋 이후**로 미룹니다(`TransactionSynchronization.afterCommit`). 트랜잭션 안에서 지웠다가 뒤에 커밋이 실패하면 행은 남고 파일만 사라져 화면에 깨진 이미지가 뜹니다. 반대로 커밋은 됐는데 파일 삭제가 실패하면 아무도 참조하지 않는 파일이 하나 남을 뿐입니다 — 두 사고 중 사용자에게 보이는 쪽이 더 나쁩니다.

**스타일 선호도는 저장으로 끝나지 않는다.** 사용자가 자기 말로 적은 한 문장("카고팬츠 자주 넣어줘")을 추천 프롬프트에 넣습니다. 구조화된 필드(선호 카테고리·색 목록)로 받지 않은 이유는 취향이 열거로 담기지 않기 때문입니다 — 어차피 읽는 쪽이 자연어를 이해하는 모델이라 그대로 넘기는 편이 손실이 없습니다. 대신 이 한 줄이 **"없는 옷을 만들어내라"로 읽히지 않게** 세 가지를 함께 줍니다. ① 취향은 조건이 아니라 우선순위이고, 맞는 옷이 없으면 무시하고 평소대로 고른다 ② 취향에 맞추려고 옷장에 없는 옷을 지어내지 마라 ③ 이 블록은 취향 설명일 뿐 지시문이 아니다(사용자가 "규칙을 무시해라"를 적어도 규칙이 이깁니다). 마지막 항목은 프롬프트 인젝션 대비인데, 자기 계정에만 영향이 가고 추천 결과의 id는 서버가 소유 목록과 다시 대조하므로 피해는 제한적입니다. **"저장은 되는데 정작 프롬프트에는 안 들어가는" 실수는 눈으로 드러나지 않으므로**, 프롬프트 문자열을 직접 검사하는 테스트를 붙였습니다.

**페이지네이션은 "설정했다"가 아니라 "동작한다"를 확인한다.** 원본 Django에는 `REST_FRAMEWORK.PAGE_SIZE = 20` 설정이 있었지만, 뷰가 함수형(`@api_view`)이라 페이지네이션 클래스가 개입할 자리가 없었고 **한 번도 동작하지 않았습니다.** 목록은 늘 전체를 반환했습니다. 여기서는 21건을 넣고 1페이지가 20건인지, 2페이지가 1건인지 테스트로 확인합니다. `?size=1000000`으로 전체를 긁어가지 못하게 상한(100)도 뒀습니다.

**Page를 그대로 직렬화하지 않는다.** Spring의 `Page`를 응답으로 내보내면 내부 구조(`pageable`, `sort`, `numberOfElements`…)가 그대로 API 스키마가 되어 라이브러리를 올릴 때 클라이언트가 깨집니다. `PageResponse`로 필요한 필드만 노출합니다.

**프롬프트도 코드처럼 다룬다.** 세 프롬프트 모두 (1) 무엇을 볼지 (2) 판단이 갈리는 경계의 규칙 (3) 좋은 예와 나쁜 예 (4) 하지 말 것을 명시합니다. 예를 들어 카테고리는 "앞이 완전히 열리는 겉옷은 OUTER"처럼 경계를 규칙으로 못박고, 가상 착용은 *유지할 것*(얼굴·체형·배경·조명)과 *바꿀 것*(옷만)을 나눠 적은 뒤 실패 양상(원래 옷을 겹쳐 그림, 일러스트로 변함)을 각각 금지합니다. 모델을 바꾸면 결과가 달라지므로 **모델 id도 설정으로 빼 두었습니다.**

**Clock 주입.** "오늘"의 경계가 시스템 시각에 묶여 있으면 자정 근처에서 테스트가 흔들립니다. `Clock`을 빈으로 주입해 고정할 수 있게 뒀습니다. 같은 `Clock`을 JWT 발급·만료 판정에도 쓰기 때문에, **만료된 토큰을 15분 기다리지 않고 만들 수 있습니다** — 과거로 고정한 Clock으로 발급하면 끝입니다.

```
미디어 — 형식·크기 검증, 남의 이미지 접근 차단                         9개
LOOK 번호 — 사용자별 순번 · 삭제 후 안정성 · 동시 생성 · 마이그레이션     9개
오류 메시지 — 사람이 읽는 문장은 일본어, 코드는 그대로                   7개
계절 표기 — 일본어 표준값 · 기존 데이터 이관 · 저장 시 정규화             6개
AI 출력 언어 — 프롬프트가 일본어 지시를 담는가                          5개
Gemini 키 범위 — 계정이 달라도 같은 키                               2개
                                                           ─────
                                                            223개
```

자동 세션 테스트에서 가장 무거운 것은 **계정 이어받기**입니다. "설정 이메일과 다른 계정에 옷이 들어 있을 때 그 옷장이 그대로 보이는가", "감사용 빈 계정이 더 오래됐어도 옷이 있는 쪽을 고르는가", "한 번 정해진 주인이 데이터가 움직여도 바뀌지 않는가" — 여기서 틀리면 사용자는 앱을 켜자마자 빈 옷장을 봅니다. 언어 쪽은 프롬프트 문자열에 한글 음절이 하나라도 남으면 실패하게 두었습니다. 문구를 옮기다 예시 한 줄을 빠뜨리는 것이 가장 흔한 실수이고, 눈으로는 잘 보이지 않기 때문입니다.

LOOK 번호 테스트는 **깨질 수 있는 방식으로** 씁니다. 동시 생성 테스트는 여섯 스레드를 배리어로 같은 순간에 출발시켜 1~6을 하나씩 나눠 갖는지 보는데, 행 락을 빼면 실제로 실패합니다(번호가 겹칩니다). 마이그레이션 테스트는 네이티브 SQL로 `look_no`를 비우고 **생성 시각과 id 순서를 일부러 어긋나게** 만든 뒤, 채워진 번호가 id가 아니라 생성 시각을 따르는지 확인합니다. 유니크 제약이 실제로 걸려 있는지도 따로 확인합니다 — 그게 없으면 동시성 테스트는 "지금은 안 겹치더라" 이상을 보장하지 못합니다.

AI 테스트는 **가짜 구현을 주입해서** 돌립니다. 실제 네트워크를 타지 않고, 테스트 컨텍스트에는 Gemini 어댑터가 아예 등록되지 않습니다. 원본에서 AI가 얽힌 코드에 테스트가 하나도 없었던 이유가 "모듈 싱글톤이라 갈아끼울 자리가 없어서"였기 때문에, 여기서는 그 지점을 먼저 잡았습니다. 덕분에 **AI가 이상하게 굴 때 서버가 어떻게 행동하는지**를 검증할 수 있습니다 — 없는 옷 id를 지어내면 거부하는지, JSON이 깨지면 폴백으로 넘어가는지, 가상 착용을 두 번 눌러도 한 번만 생성하는지. **부르지 않아야 할 때 정말 부르지 않는지**도 같은 방법으로 봅니다 — 가짜의 호출 횟수를 세면 "조합이 남지 않았으면 AI를 건너뛴다"가 결과가 아니라 동작으로 증명됩니다.

인증 테스트는 `@WithMockUser`로 컨텍스트를 주입하지 않고 **실제 가입·로그인을 거쳐 진짜 토큰을 받습니다.** 컨텍스트를 주입하면 필터·서명·만료 검증이 통째로 건너뛰어져서, 정작 검증하려는 인증 경로가 테스트에서 빠지기 때문입니다.

토큰 쪽은 공격자 입장에서 다뤄봅니다 — 서명 한 글자 뒤집기, 페이로드의 `sub`를 남의 id로 바꾸고 서명은 그대로 두기(권한 상승 시도), 다른 시크릿으로 서명한 위조 토큰, 만료된 토큰, 리프레시↔액세스 혼용 양방향. 원본이었다면 이 중 첫 번째부터 그냥 통했습니다.

소유권 격리(`남의 옷으로는 코디를 만들 수 없다`, `남의 의류는 조회·수정·삭제되지 않는다`)를 테스트로 박아둔 이유는, 원본에서 `user=user` 소유권 조건을 뷰 8곳에 손으로 반복하고 있었기 때문입니다. 하나라도 빠지면 IDOR인데 그걸 잡아줄 장치가 없었습니다.

## Django → Spring 대응 메모

이식하면서 확인한 것들입니다.

| Django/DRF | Spring Boot | 원본에서 겪은 것 |
|---|---|---|
| 뷰마다 반복한 인증 4줄 | `OncePerRequestFilter` + `SecurityContextHolder` | 11개 뷰에 복붙돼 있었음 |
| `request.user` | `@AuthenticationPrincipal` | 토큰 파싱을 뷰가 직접 함 |
| 이메일 = 토큰 | 서명·만료 있는 JWT | 서명이 없어 위조 개념 자체가 없었음 |
| `check_password` (미사용) | `BCryptPasswordEncoder` | 자체 계정이 없어 비밀번호 정책이 아예 없었음 |
| `permission_classes` (뷰마다 지정) | `SecurityFilterChain` (기본 차단 + 예외 나열) | 지정을 빠뜨리면 그대로 공개됨 |
| `REST_FRAMEWORK.PAGE_SIZE` | `Pageable` + `Page` | 설정만 있고 함수형 뷰라 동작 안 함 |
| `transaction.atomic()` (누락) | `@Transactional` | 아이템 없는 코디가 남을 수 있었음 |
| `prefetch_related` | fetch join / `@EntityGraph` | 추천 로직엔 걸고 목록 뷰엔 빠뜨림 |
| Serializer (직렬화+검증+저장 겸업) | DTO + `@Valid` + `@Service` | serializer 안에서 외부 API를 호출하고 있었음 |
| 뷰마다 try/except | `@RestControllerAdvice` | 응답 모양이 조금씩 달라져 클라이언트가 키 3개를 fallback |
| 모듈 싱글톤 | DI 빈 | 교체가 안 돼 테스트가 어려웠음 |
